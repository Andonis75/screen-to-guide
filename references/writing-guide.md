# 从识别材料到可操作指南

## 写作目标

读者不知道录屏内容，也能按说明完成相同任务。正文围绕“在哪里、做什么、填什么、接下来出现什么”组织，不围绕识别模型的观察过程组织。

交付前必须做流程整理。`run.py` 的逐帧模型结果是初稿；只删除“待复核”标签，或者把“画面显示”机械替换成“点击”，都不算整理完成。

## 制作顺序

1. 通读画面与转写，写一句话说明这段录屏完成什么任务。
2. 整理起点、所需资料、完整操作顺序和完成标志。
3. 对出现跳转、选项改变、输入、发送/保存的地方回看前后片段。选取能看清相关按钮和设置的实际截图，保持来源时间。
4. 按读者任务合并步骤：一组连续填写可以归为一步，等待加载不单独成步；异常分支单独说明触发条件和解决操作。
5. 用界面的真实字段名与按钮名写动作。动作一条一个，必要时写出菜单路径。
6. 区分示例参数和通用操作。录屏里的日期、商品 ID、费率、账号等不能无说明地变成所有人的默认值。
7. 把技术日志、识别原文、审阅状态和来源说明留在 JSON/analysis 中；阅读正文只保留操作需要的提示。
8. 从头走读：如果读者还要猜“点哪里/填哪项/怎么继续”，补齐；如视频确实缺失关键条件，只说明那项具体缺口。

动作依据与交付前复审见 [action-evidence.md](action-evidence.md)。先完成事件顺序及自动/主动分类，再写操作指令；最终教程启用严格动作校验。不要把后续页面跳转补写成一次没有观察到的点击。

## Manifest 阅读版字段

保留 schema_version 1 的现有字段，新增可选字段。所有文本均为纯文本，不接受 HTML。

```json
{
  "tutorial": {
    "action_evidence_required": true,
    "summary": "说明读者能完成的任务。",
    "prerequisites": ["已登录相应账号。", "准备好要填写的资料。"],
    "example_settings": [{"label": "配置项", "value": "本次示例值，实际按任务填写"}],
    "completion": "描述完成时能看到的提示或产物。"
  },
  "steps": [{
    "title": "用动作命名，如添加要推广的商品",
    "description": "一句必要的背景或目的，避免复述标题。",
    "actions": ["点击“添加商品”。", "搜索目标商品，勾选后点击“添加”。"],
    "outcome": "商品出现在列表中，可以继续设置。",
    "tip": "仅在有实际操作价值时填写。"
  }]
}
```

示例只展示阅读字段；实际每步仍必须包含真实的 `id`、`frame_ids`、`timestamp_seconds`、`image` 及逐条对应的 `action_refs`，顶层包含 `action_evidence`。字段与示例见动作依据规范。截图引用与时间校验继续生效。

`review_status` 保留内部默认值，不伪装为用户确认。Agent 检查视频后在 `processing.agent_review` 中记录检查范围与材料，正文不强迫读者逐条处理这些制作记录。未完成必要视频检查时不要添加 `tutorial` 来伪装完成。

## 文案例子

较差：画面显示已选择 6/50 位达人。需核对当前筛选与勾选是否正确。

较好：勾选要邀约的达人，再点击“批量邀请”。本次选了 6 位；界面的 50 表示一批最多可选 50 位。

较差：截图本身未记录按钮的完整点击过程，需要用户回看确认。

处理方式：Agent 回看前后片段，确认选项、按钮和后续页面，然后写出操作顺序。视频中没有出现的结果不编造；可以描述按钮执行的明确功能，不宣称对方已阅读或接受。

## 发布前走读

- 标题能看出任务，开头写明起点和准备项。
- 每步有动词、准确的界面名称、必要的输入说明。
- 截图与步骤对应，有视频时间入口。
- 没有把用户账号、长 ID、订单等无关信息大量抄进正文。
- 没有空白加载、重复观察、原始转写错词和“需核对”堆积。
- 例子、操作规则和结果分别写清楚。
- HTML 实际打开正常，Markdown 同样是完整的阅读文档。
